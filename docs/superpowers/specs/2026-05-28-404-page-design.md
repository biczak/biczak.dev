# 404 Page — Design Spec

**Date:** 2026-05-28
**Status:** Draft — pending user review
**Owner:** Alex Biczak
**Domain:** biczak.dev
**Relates to:** v1.0.0 release

## Overview

Cloudflare Pages production verification (Phase 4 of the v1.0 deploy plan) surfaced a real bug: requests to non-existent paths on `biczak.dev` return the homepage with HTTP 200 OK, rather than a proper 404 status with a dedicated page. This causes "soft 404" SEO penalties and degrades user trust when crawlers and visitors discover broken links.

This spec defines a minimal 404 page consistent with the portfolio's existing voice, plus the Cloudflare Pages configuration needed to return the correct HTTP status.

## Goals & Non-Goals

### Goals
- Ship before v1.0.0 tag — soft 404s start hurting SEO from the first crawl.
- Match the existing site's voice (in-character, terminal-aesthetic, slightly poetic).
- Offer recovery links so a confused visitor can self-rescue.
- Return HTTP 404 status, not 200.
- Reuse `BaseLayout` for visual consistency and to inherit existing perf optimizations.

### Non-Goals
- Suggested-page recommendations based on the requested URL.
- 404 analytics (the URLs that 404 are interesting but out of scope here; Web Analytics' built-in pageview tracking will surface the volume).
- A 500 / generic error page (separate concern, not surfaced as a real problem yet).
- Soft-404 monitoring / alerting.

## Current Behavior

`curl -sI https://biczak.dev/this-page-does-not-exist` currently returns:
```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
```

…with the homepage's HTML body (title, hero section, full content). Root cause: no `src/pages/404.astro` exists, no `public/_redirects` configures fallback. Cloudflare Pages' default behavior with no 404.html and no _redirects rule is to serve `index.html` with status 200.

## Design

### File 1: `src/pages/404.astro` (new)

```astro
---
import BaseLayout from '@/layouts/BaseLayout.astro';
import Header from '@/components/Header.astro';
import Footer from '@/components/Footer.astro';
---

<BaseLayout title="404 · Alex Biczak" description="Page not found.">
  <Header />
  <main>
    <section class="mx-auto max-w-6xl px-6 pt-32 pb-24 md:pt-48 md:pb-32">
      <p class="font-mono text-xs uppercase tracking-[0.2em] opacity-60 mb-8">
        ~/alex-biczak/404
      </p>
      <h1 class="font-display font-bold text-5xl md:text-7xl lg:text-[88px] leading-[1] tracking-[-0.04em] mb-8">
        This route doesn't exist&hellip;yet.
      </h1>
      <ul class="flex gap-6 font-mono text-sm">
        <li><a href="/" class="hover:text-cyan hover:underline transition-colors duration-quick">[ home ]</a></li>
        <li><a href="/tools" class="hover:text-cyan hover:underline transition-colors duration-quick">[ tools ]</a></li>
        <li><a href="/#contact" class="hover:text-cyan hover:underline transition-colors duration-quick">[ contact ]</a></li>
      </ul>
    </section>
  </main>
  <Footer />
</BaseLayout>
```

Notes:
- Reuses `BaseLayout`, `Header`, `Footer` — no new layout primitives.
- H1 copy: "This route doesn't exist…yet." (tight, slightly poetic, hint of future expansion).
- Eyebrow `~/alex-biczak/404` echoes the header logo's terminal aesthetic and orients the visitor.
- Link labels `[ home ]`, `[ tools ]`, `[ contact ]`. Hover state: text shifts to cyan + underline appears. Two simultaneous affordances ensures interactivity is unambiguous (color-only would fail for ~8% of male visitors with color-vision deficiencies).

### File 2: `public/_redirects` (new)

```
/* /404.html 404
```

Single rule: for any path that doesn't match a real file in `dist/`, serve `dist/404.html` and respond with status code 404. Cloudflare Pages reads this file at build time and applies the rule at the edge — no Pages function invocations needed.

## Acceptance Criteria

1. `curl -sI https://biczak.dev/this-page-does-not-exist` returns `HTTP/1.1 404 Not Found`.
2. The 404 page renders with the same header, footer, and color tokens as the homepage.
3. All three recovery links are functional — `/`, `/tools` (which redirects to `/tools/`), and `/#contact` scroll-anchors into the homepage's contact section.
4. Hover on any recovery link triggers both color shift to `text-cyan` AND underline appearance.
5. No regression on existing routes: homepage, `/tools/`, `/tools/easing/` continue to return 200 with their normal content.
6. Existing E2E tests pass. (Axe scans currently cover homepage, /tools, /tools/easing — we may extend to /404 as a v1.0.1 follow-up.)
7. CI green: typecheck, lint, format, unit tests, build, Playwright E2E, Lighthouse (per existing gates).

## Out of Scope (v1.0.1 candidates)

- Add `/404` to the axe-tested E2E routes.
- Add a Web Analytics annotation or custom event for 404s (manual analytics mode required, which we've ruled out for v1.0).
- Smarter 404 (e.g., "did you mean /tools?" based on Levenshtein distance from the requested path).
